# Project Recovery Specification

## Goal
Recover and rebuild the current real estate reservation system into a stable, production-ready platform.

## Critical Rules
- Do not delete old files.
- Do not add new features before audit.
- Do not use mock data in production screens.
- Do not use localStorage for business-critical data.
- Preserve useful backend logic.
- Preserve old files by archiving them if needed.
- Arabic RTL must remain the default.
- Owner, Admin, Assistant, and Client flows must all work.

## Required Execution Order
1. Full project audit
2. Backup commit
3. File organization
4. Backend recovery
5. Database/schema review
6. API standardization
7. Frontend rebuild
8. Role dashboards
9. Media/updates cleanup
10. Testing

## Full Requirements
المشروع حاليًا أصبح يحتوي على مشاكل كثيرة:
- ملفات غير مكتملة
- ملفات لا تعمل
- أجزاء Frontend مكسورة
- واجهة صعبة الاستخدام للأدمن والمساعدين
- أكواد متداخلة
- ملفات قديمة وغير واضحة
- وظائف تبدو Demo أو غير مربوطة جيدًا
- تجربة استخدام غير مناسبة للتشغيل الحقيقي

المطلوب الآن:
إيقاف إضافة أي Features جديدة مؤقتًا، وتنفيذ Project Recovery شامل.

مهم جدًا:
- لا تحذف أي ملفات قديمة مباشرة.
- لا تكسر الباك إند الموجود.
- لا تضف مميزات جديدة قبل تنظيف المشروع.
- لا تستخدم Mock Data في الواجهات الأساسية.
- لا تستخدم localStorage للبيانات المهمة.
- لا تترك أي كلام يدل أن المشروع Demo أو AI.
- حافظ على اللغة العربية و RTL.
- الهدف هو تحويل المشروع إلى نظام حقيقي سهل الاستخدام للمالك، الأدمن، المساعد، والعميل.

==================================================
المرحلة 1 — Audit شامل للمشروع
==================================================

قبل كتابة أي كود جديد، افحص المشروع بالكامل.

اعمل تقرير شامل يحتوي على:

1. الملفات المهمة التي تعمل
2. الملفات غير المكتملة
3. الملفات المكررة
4. الملفات غير المستخدمة
5. الملفات التي تسبب مشاكل
6. أجزاء Frontend المكسورة
7. أجزاء Backend الحقيقية
8. أجزاء Backend الوهمية أو الناقصة
9. API endpoints الموجودة
10. API endpoints غير المستخدمة
11. الصفحات المتصلة بالباك إند
12. الصفحات التي لا تزال تستخدم Mock أو localStorage
13. مشاكل التصميم وتجربة الاستخدام
14. مشاكل صلاحيات Owner / Admin / Assistant / Client

اعرض التقرير في جدول:

- File / Area
- Status: Working / Partial / Broken / Unused / Legacy
- Problem
- Keep / Refactor / Archive / Replace
- Notes

ممنوع تبدأ تنفيذ قبل ما تخلص الـ Audit.

==================================================
المرحلة 2 — Backup وحماية الملفات القديمة
==================================================

قبل أي تعديل:

نفذ:
git add .
git commit -m "backup-before-project-recovery"

بعدها لا تحذف الملفات القديمة.

أنشئ مجلد:

/legacy

أو:

/archive/old-version

وانقل إليه فقط الملفات التي:
- غير مستخدمة
- مكررة
- قديمة
- تسبب تضارب
- ليست مطلوبة في النسخة الجديدة

لكن لا تحذفها.

أي كود مفيد يتم استخراجه وإعادة استخدامه في النسخة الجديدة.

==================================================
المرحلة 4 — Backend Recovery
==================================================

افحص الباك إند الحالي ولا تعتبره Production لمجرد وجود Routes.

كل Endpoint لازم يعمل فعليًا:

1. Authentication check
2. Role permission check
3. Input validation
4. Read/write from database
5. Return standard JSON response
6. Audit log for important actions

وحّد شكل الردود:

Success:
{
  "success": true,
  "data": {},
  "message": "تمت العملية بنجاح"
}

Error:
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "رسالة واضحة بالعربية"
  }
}

طوّر الباك إند ليغطي:

- تسجيل الدخول
- تسجيل الخروج
- بيانات المستخدم الحالي
- صلاحيات Owner / Admin / Assistant
- العملاء
- الشقق
- الصفقات Deals
- طلبات الموافقة
- المدفوعات
- الأقساط
- العقود
- الإيصالات
- آخر التحديثات
- الصور والفيديو
- الإعدادات
- سجل النشاط
- التقارير

ممنوع وجود Fake Success.
أي عملية تقول Success لازم تكون كتبت أو قرأت فعليًا من قاعدة البيانات.

==================================================
المرحلة 5 — قاعدة البيانات
==================================================

لو النظام الحالي يستخدم SQLite فقط، جهّزه ليعمل على PostgreSQL للإنتاج.

استخدم:
DATABASE_URL

أضف:
.env.example

مثال:
DATABASE_URL=postgresql://user:password@localhost:5432/real_estate_db
SECRET_KEY=change-this-secret
APP_ENV=development
UPLOAD_FOLDER=static/uploads

الجداول المطلوبة:

- users
- apartments
- clients
- deals
- payments
- installments
- contracts
- receipts
- project_updates
- media_assets
- settings
- audit_logs

مهم:
- لا تعتمد على localStorage لأي بيانات مهمة.
- localStorage مسموح فقط للأشياء المؤقتة أو UI preferences.
- العقود والمدفوعات والعملاء والشقق لازم في Database.

==================================================
المرحلة 6 — Frontend Rebuild منظم
==================================================

أعد بناء الواجهة بشكل احترافي وسهل الاستخدام.

لا تصلّح الواجهة القديمة Patch فوق Patch.
ابنِ واجهة منظمة باستخدام الملفات الجديدة مع إعادة استخدام المفيد من القديم.

المستخدمون الأساسيون:

1. Owner — المدير الرئيسي
2. Admin — مسؤول التشغيل
3. Assistant — مساعد مبيعات
4. Client — العميل

كل مستخدم له واجهة واضحة ومحدودة.

==================================================

==================================================

المالك يرى:

1. لوحة المدير الرئيسي
- ملخص الشقق
- المبيعات
- المحصل
- المتبقي
- الديلات بانتظار الموافقة
- الأقساط المتأخرة
- أداء المساعدين
- تنبيهات مهمة

2. طلبات الموافقة
- عرض ديلات المساعدين
- موافقة
- رفض
- طلب تعديل
- إصدار عقد نهائي
- رؤية العقد المسودة
- مراجعة مخاطر الديل

3. العملاء والشقق
- كل العملاء
- كل الشقق
- خريطة المبنى
- المدفوعات
- العقود

4. الإعدادات
- بيانات المكتب
- صيغة العقد
- الأسعار والحدود الدنيا
- صلاحيات المساعدين
- رقم واتساب
- الإيصالات
- آخر التحديثات

5. سجل النشاط
- كل العمليات
- فلترة حسب المستخدم
- فلترة حسب التاريخ
- عرض تفاصيل قبل وبعد التعديل

==================================================
واجهة Admin
==================================================

الأدمن يحتاج واجهة سهلة يومية، لا تكون معقدة.

تبويبات Admin:

1. لوحة الإدارة
- ملخص سريع
- عملاء جدد
- شقق متاحة
- مدفوعات اليوم
- دفعات قيد المراجعة

2. العملاء والشقق
- إدارة العملاء
- عرض الشقق
- بحث وفلترة
- عرض بيانات العميل
- تحميل كشف الحجز

3. المدفوعات
- إضافة دفعة
- تأكيد دفعة
- رفض دفعة
- تحميل إيصال
- سجل المدفوعات

4. العقود
- إنشاء عقد
- اختيار عميل موجود
- ملء بيانات تلقائيًا
- معاينة
- طباعة
- PDF
- حفظ في Database

5. آخر التحديثات
- إضافة تحديث
- رفع صورة/فيديو
- نشر/مسودة

6. بيانات الدخول
- بيانات الحساب

==================================================
واجهة Assistant
==================================================

واجهة المساعد لازم تكون بسيطة جدًا.

المساعد يرى فقط:

1. لوحة المساعد
- ديلاتي
- ديلات بانتظار الموافقة
- ديلات مطلوب تعديلها
- ديلات تمت الموافقة عليها
- ديلات مرفوضة

2. إنشاء ديل جديد
- بيانات العميل
- اختيار الشقة
- السعر المقترح
- المقدم
- طريقة السداد
- الأقساط
- ملاحظات
- حفظ مسودة
- إرسال للموافقة

3. الشقق المتاحة
- يرى فقط المتاح
- لا يرى تقارير مالية
- لا يرى كل العملاء
- لا يرى إعدادات

4. عقد مسودة
- يقدر يطبع أو يحمل عقد مسودة فقط
- يجب أن يظهر عليه:
مسودة غير نهائية - بانتظار موافقة الإدارة

المساعد ممنوع:
- يوافق على ديل
- يصدر عقد نهائي
- يغير حالة الشقة إلى مباعة
- يرى سجل النشاط الكامل
- يرى إعدادات النظام
- يرى كل المدفوعات
- يرى تقارير مالية شاملة

==================================================
المرحلة 7 — UX Simplification
==================================================

المشروع لازم يكون سهل الاستخدام.

طبّق هذه القواعد:

- كل صفحة لها عنوان واضح.
- كل زر له وظيفة واضحة.
- لا تكدس معلومات كثيرة في صفحة واحدة.
- استخدم Tabs داخلية بدل صفحات طويلة.
- استخدم Cards للملخصات.
- استخدم Tables للبيانات الكبيرة.
- استخدم Modals للتفاصيل.
- استخدم Search و Filters في كل جدول.
- استخدم Empty State واضح.
- استخدم Loading State.
- استخدم Error State.
- استخدم Toast للنجاح والخطأ.
- كل عملية خطيرة لها Confirm Dialog.

أمثلة Empty States:

لا توجد بيانات متاحة حاليًا.
لا توجد طلبات موافقة في الوقت الحالي.
لا توجد تحديثات منشورة حاليًا.
لا توجد سجلات نشاط مطابقة للبحث.

لا تستخدم صور وهمية.

آخر التحديثات:
- لا يوجد Demo.
- تظهر فقط من Database.
- لو لا يوجد تحديثات منشورة، يظهر Empty State.
